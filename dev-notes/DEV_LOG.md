## 1. 프롬프트 다듬기

처음에는 해커톤 프롬프트에 기억과 정정 규칙을 덧붙였다. 이후 성격부터 다시 잡으면서 쉬운 한국어 반말과 짧은 감정 표현을 중심으로 고쳤다.

무무의 기획 의도는 긍정과 공감을 기반으로 사소한 이야기를 편하게 주고받는 것이었다. 이 기준으로 직접 대화해보니, 말투가 다정하다고 해서 대화가 자연스럽게 이어지는것이 아니었다.

--

### 과도한 긍정과 공감

초기 프롬프트는 긍정과 공감을 많이 하도록 작성했었다. 그러자 사용자가 같은 고민을 반복하여 말해도 무무는 “힘들겠다”, “답답하겠다”처럼 표현만 바꿔 반응했다. 이미 한 말을 여러 번 설명해야 했고, 대화가 진행되지 않았다.

대화가 빙빙 돈다고 지적해줘도 빙빙돈다는 표현에 집중하여 “우와, 신난다!”라고 긍정적인 답변을 한 사례도 있었다. 상황과 맞지 않는 밝은 반응까지 나온 것이다. 

이것은 "편하게 대화하는 말동무" 라는 초기 기획의도를 완전히 벗어난 "가르쳐 주어야 하는 대상"이 되는 것이다.

공감/긍정 표현을 많이 넣는 것보다, 사용자가 지금 무엇을 말하고 있는지 먼저 파악시켜야 했다.

--

### 사용자가 대화를 모두 이끌게 되는 문제

반응을 보완하려고 사용자의 답변과 피드백에 따라 답변과 대화의 방향을 전환하는 프롬프트로 개선하려 생각했다.
그러나 다음 이야기를 어떻게 할지 매번 사용자의 답변에 따라 바뀐다면, 무무는 대화의 리드를 기다리기만 하는 수동적인 상태가 된다.

무작정 공감하는 문제를 고치더라도 사용자가 대화의 방향을 계속 정해줘야 하는 상황을 피하고 싶었다. 화제가 막힌다고 판단 될 때마다 새 주제로 넘어가게 하는 방법도 검토했지만, 이 또한 매번 다른 이야기로 흐르면서 대화가 산만해질 수 있었다.

최종 프롬프트에는 현재 이야기 안에서 무무 자신의 생각이나 관찰을 짧게 보태도록 설계했다. 질문을 할 때는 무작정 질문하는것이 아닌, 실제로 확인할 내용이 있거나 맥락을 파악할 때 하도록 설계했고, 화제를 바꿀 때는 급작스럽지 않고 완만하게 진행하도록 하였다.

--

### 말투와 상황 판단의 균형

**당연하지만, 무무가 어린아이처럼 말하더라도, 대화를 이해하고 판단하는 능력까지 어린아이 수준으로 제한해서는 안된다.**

해커톤 당시에는 어린아이와 같이 행동하는 것에 매몰되어 하나하나 알려주고, 이끌어 줘야하는 정말 수동적인 존재로 프롬프를 구축하였다.

하지만 매번 뜻을 설명해줘야 하거나, 이미 알려준 조건을 놓치고, 다음에 무슨 말을 해야 할지 계속 묻는다면 사용자에게 부담이 될 수 있다. 편하게 이야기하려고 들어온 사용자가 오히려 무무를 돌봐야 하는 상황이 되는 것이다.

그래서 "어린이다움"은 무무의 성격, 어휘, 반말, 호기심, 짧은 감정 등 표현하는 방식에 담았다. 

반대로 질문의 뜻을 읽고 앞선 조건을 함께 고려하는 부분은 충분히 어른스럽게 판단하도록 작성했다.

--

### 자연스러운 대화를 위해 바꾼 것

| 겪은 문제 | 프롬프트에 반영한 내용 |
|---|---|
| 긍정과 공감의 반복 | 이미 공감한 고민이 다시 나오면 같은 감정을 바꿔 표현하는 것에 그치지 않고, 상황에 맞는 생각이나 관찰을 짧게 보태기 |
| 질문에 부적절한 답변 | 현재 발화가 질문인지, 감정이나 일상을 나누는 말인지 먼저 살피고 질문에는 요점부터 답하기 |
| 수동적인 대화 | 이야기에서 이어지는 반응이나 생각을 보태고, 확인이 필요한 질문은 한 번에 하나씩 하기 |
| 과도한 화제전환 | 같은 주제 안에서 대화를 이어가고, 사용자가 새 주제를 꺼내거나 전환을 원하는지 살피기 |
| 난잡한 답변 | 가벼운 반응은 한 문장, 설명은 보통 두 문장, 길어도 네 문장 안으로 답하기 |
| 상황에 맞지 않는 감탄 | 상대가 고민을 이야기 할 때 들뜬 감탄사를 쓰지 않고, 자신의 감정은 짧게 표현하기 |

초반에 사용자의 상황을 모르면 가벼운 질문으로 상대를 파악하지만, 정보수집을 위해 고정된 턴을 할당하지 않았다. 
대화를 통해 자연스럽게 정보를 수집하는 것이다.

물론 이것들을 반영한다고 해서 완벽해질 수는 없었지만, 해커톤 당시의 무무보다 훨씬 더 자연스러운 대화를 이어갈 수 있었다.

### 현재 LLM 설정

LangChain으로 모델을 연결하고, 무무가 어떤 정보를 참고하여 어떤 말투로 답할지는 대화 이력과 시스템 프롬프트로 전달한다.

| 전달하는 내용 | 용도 |
|---|---|
| 시스템 프롬프트 | 무성의 초등학교 중학년 캐릭터, 말투, 맥락 판단, 답변 길이와 대화 제한 |
| 현재 대화 이력 | 앞에서 나눈 말과 지금 추가된 조건을 함께 참고 |
| RAG로 찾은 과거 대화 | 관련 있는 이전 이야기와 사용자가 알려준 내용을 참고 |
| 현재 사용자 입력 | 이번에 답할 대상. 과거 기록과 내용이 다르면 현재 입력을 우선 |

특히 시스템 프롬프트에서는 정치적·선정적인 내용과 연애감정을 유도하는 표현은 제한하고, 가능한 기능의 범위도 함께 적었다. [현재 시스템 프롬프트](../SYSTEMPROMPT.txt)

## 3. TTS 보이스 모델 탐색과 보류
기존의 무무는 Supertone에서 서비스했던 Supertone Play서비스를 사용했었다.

Supertone Play는 풍부한 감정표현과 세부 파라미터 조정으로 다양한 목소리를 빠르고 편리하게 튜닝하여 사용할 수 있었다. 때문에 짧은 기간동안 무무의 어리고 호기심 많은 목소리와 걱정하는 목소리, 기쁜 목소리 등을 쉽게 마련할 수 있었다.(이래도 되나 싶을만큼 완성된 보이스 모델을 아주 적은 비용으로 굉장히 쉽게 사용할 수 있었다.)


하지만 Supertone Play 서비스가 `2026.08.31.` 서비스를 종료하였고, 이를 대체할 한국어 보이스 모델을 탐색하였었다.

Typecast, NEVER CLOVA 등 다른 한국기업의 서비스는 Supertone Play대비 가격대가 부담이었다.
Supertonic 3, Elevenlabs 등 여러 다른 무료 서비스를 살펴보기도 하였고,
HuggingFace에서 직접 Qwen3-TTS의 음색 설계를 하거나 Chatterbox의 표현 강도·페이스도 살펴보는 등 파인튜닝까지 해보았다.

결국 Supertone Play를 만족스럽게 대체할 만한 보이스 모델을 찾지 못하였고, 직접 보이스 모델을 튜닝하여 기업에서 감정연기 튜닝까지 끝내둔 모델을 대체하기에는 지나치게 시간이 오래걸린다고 판단하여 TTS는 보류, 텍스트로만 무무의 답변을 출력하고 음성 입력과 답변의 품질을 높이기에 집중하기로 결정하였다.

## 4. 대화 이력 전달과 로컬 임베딩, RAG

해커톤 당시에는 현재 대화 이력을 다음 프롬프트에 계속 이어붙였다. 대화를 끝내면 원문은 `log_DB`, 일기는 `diary_DB`(두 가지 모두 폴더명이다)에 `.txt` 파일로 저장했었다. 또한 저장한 파일은 순전히 열람용 이었고, 이전에 나눈 대화를 현재 대화에 연결하는 기능이 전혀 없었다.

| 항목 | 해커톤 웹 | 현재 Flask 버전 |
|---|---|---|
| 진행중인 대화 | 현재 이력을 프롬프트에 이어 붙혀 전달 | 답변 생성에 성공한 턴을 이력으로 전달 |
| 대화 종료 | 원문과 일기를 텍스트 파일로 저장 | 원문과 검색용 벡터, 일기를 SQLite에 저장 |
| 다음 대화 | 현재 세션 이력으로 응답 | 같은 브라우저의 과거 기록에서 관련 구간을 최대 3개 찾아 참고 |
| 일기장 | 일기형태의 요약본 열람 | 일기형태의 요약본 열람, 해당 대화 전문을 채팅창 형태로 열람|

기존에는 없던 이전 대화를 기억하는 기능이 추가되기도 하였고, Gemini 자체적으로 현재 진행중인 대화의 맥락은 자동적으로 파악되기 때문에(당시 사용한 Llama-4-meverick도 가능했지만, 기능 구현에 매몰되어 굳이 프롬프트를 길어지게 만들었었다...)현재 대화는 따로 넘기지 않고, 이전 대화는 간단한 RAG를 탑재하여 조그 더 효율적으로 이전 대화를 기억하게 하였다.


## STT 모델 설정을 위한 비교 테스트

### STT선정 과정

원본 Whisper small (이하 `small`) 에 한국어 데이터를 추가 학습한 두 모델을 비교했고, 최종적으로는 `small`을 선택했다.
이하 AH 튜닝이라고 부른 것은 [`AI Hub 109번 자유대화 데이터`](https://aihub.or.kr/aihubdata/data/view.do?dataSetSn=109)로 학습한 모델이고,
KS 튜닝은 [`AI Hub 123번 KsponSpeech`](https://aihub.or.kr/aihubdata/data/view.do?dataSetSn=123)로 학습한 모델이다.

### AI_Hub 자유대화 파인튜닝

끝말잇기 진행 당시 `차표`를 `잡혀`로 인식하였다. 비슷하게 연음/탈락 등에서 불안정한 집계가 많았다.

또한 로딩시간을 줄이기 위해서 AI Hub의 한국어 자유대화 샘플을 받아 원본 `openai/whisper-small`에 추가 학습을 했다.

WAV와 JSON 전사를 연결하고, 같은 화자가 학습과 평가 양쪽에 들어가지 않도록 나눴다. [첫 학습 노트북](../notebooks/whisper-finetuning.ipynb)

| 항목 | 설정 및 결과 |
|---|---|
| 학습 | 화자 3명, 발화 1,079개, 약 2시간 |
| 학습 설정 | 1 epoch, 학습률 1e-5, 난수 시드 42 |
| 평가 | 학습에 없는 화자 1명, 발화 120개, 0.26시간 |
| CER | `base` 5.55%, 파인튜닝 4.18%, 차이 1.37%p |

평가에서는 두 모델에 같은 생성 설정을 썼다.

### 문장분호 문제

마이크로 비교해보니 기존 `base`보다 의문문의 물음표가 더 자주 빠졌고, 받아쓰기 자체도 좋아졌다는 느낌이 들지 않았다.

학습 ZIP을 확인해보니 학습 전사 1,079개와 평가 전사 120개 모두에 ASCII·전각 물음표가 하나도 없었다.

의문문을 배제하고 대화를 할 수 없기 때문에 문장부호가 있는 데이터로 다시 학습하여 진행하기로 했다.


### KsponSpeech 파인튜닝

문장부호가 있는 KsponSpeech로 원본 `small`을 처음부터 다시 학습했다. (학습 발화 1,812개 - 약 2시간 분량) 별도 `eval_clean` 120개를 의문문과 평서문 각 60개로 구성해 같은 추론 설정으로 비교했다. [KsponSpeech 학습 노트북](../notebooks/whisper-ksponspeech.ipynb)

| 지표 | 원본 small | KsponSpeech 파인튜닝 |
|---|---:|---:|
| CER | 10.63% | 9.33% |
| 물음표 누락 | 17/60 | 13/60 |
| 물음표 오삽입 | 6/60 | 7/60 |

웹에서 두 모델을 골라 쓸 수 있게 연결였고, `small`, `AH튜닝`, `KS튜닝` 모두 직접 마이크로 비교하여 사용해보았다.

결론적으로 원본 `small`이 더 낫다고 판단하였다.
