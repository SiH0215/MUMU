## 1. 텍스트 멀티턴 복원

11월 13일에는 기존 시스템 프롬프트를 그대로 가져와 텍스트 대화부터 연결했다. 시스템 메시지를 맨 앞에 두고, 성공한 사용자 발화와 답변을 다음 요청에도 전달했다. 실패하거나 빈 답변을 받은 턴은 모델의 대화 이력에 넣지 않았다.

처음에는 watsonx 초안이 있었지만 LangChain의 `init_chat_model()`과 Gemini를 쓰는 쪽으로 바꿨다. 연결 과정에서 프로젝트의 `.env`보다 터미널에 남아 있던 예전 키를 먼저 읽어 결제 한도 오류가 났다. 프로젝트 키를 직접 전달하도록 바꾼 뒤 두 턴의 실제 응답을 확인했다.

두 번째 요청이 `system → human → ai → human` 순서로 전달되는 것도 확인했다. 다만 이력이 정상적으로 전달돼도 이전 내용을 묻는 질문에 답이 빗나가는 경우가 있었다.

## 2. 무무 프롬프트 다듬기

처음에는 해커톤 프롬프트에 기억과 정정 규칙을 덧붙였다. 이후 성격부터 다시 잡으면서 쉬운 한국어 반말과 짧은 감정 표현을 중심으로 고쳤다.

어린이다운 말투를 쓰면서도 질문의 뜻과 앞선 맥락은 충분히 이해하도록 지시했다. 사용자가 대화를 끝내려 하면 새 질문을 붙이지 않고 인사하도록 했다. CLI의 종료 명령은 `/exit`다.

11월 16일의 프롬프트는 스냅샷에서 볼 수 있다. 이후 수정한 프롬프트는 루트의 `SYSTEMPROMPT.txt`에 있다. [당시 프롬프트](snapshots/02-gemini-voice-2026-11-16/SYSTEMPROMPT.txt)

## 3. 고정 녹음에서 발화 단위 입력으로

해커톤 웹에서는 말의 길이에 상관없이 16kHz로 5초를 녹음했다. 짧게 말해도 남은 시간을 기다려야 했고, 길게 말하면 끝이 잘렸다. 별도로 정리한 코드에는 Whisper 모델을 재사용하는 처리가 있었다.

11월 16일 버전에서는 Silero VAD를 붙여 말의 시작과 끝을 감지했다. 당시에는 녹음 스레드와 답변 처리를 나눠 답변을 기다리는 동안에도 마이크를 읽었다. 입력이 넘치면 버퍼를 비웠고, 처리할 발화가 쌓여 대기열이 가득 차면 건너뛴 발화가 있다고 표시했다. 이후 마이크를 잠시 멈추는 방식으로 바꿨다.

- 음성은 16kHz 모노 PCM으로 받고, 512샘플씩 VAD에 넣었다. 한 프레임은 32ms다. 당시 Whisper 기본 모델은 `base`였다. 모델은 시작할 때 한 번만 불러오고, 임시 녹음 파일 없이 파형 배열을 넘겼다. [당시 voice.py](snapshots/02-gemini-voice-2026-11-16/voice.py)
- 발화 시작 임계값은 0.50, 유지 임계값은 0.35로 정했다. 시작 전 최대 224ms를 붙이고, 800ms 동안 말소리가 없으면 한 턴으로 넘겼다. 기다리는 중 다시 말하면 이어 붙였다. 끝의 무음은 약 96ms만 남겼고, 아주 짧은 감지 신호는 버렸다. [당시 turns.py](snapshots/02-gemini-voice-2026-11-16/turns.py)
- Windows에서 한글 경로의 Silero TorchScript 파일을 직접 열 때 오류가 났다. 파일을 바이트로 읽어 메모리 버퍼로 넘기는 방식으로 해결했다.

## 4. STT 비교와 검증 결과

같은 WAV를 5초 고정 녹음, Silero 기본 이벤트, 무무의 800ms 종료 기준에 각각 넣어 비교했다. CER, 말이 끝나기 전에 입력이 끊긴 횟수, 인식하지 못한 발화, 무음을 말로 인식한 경우를 집계했다. 대기 시간은 WAV에서 감지한 말끝과 Whisper 처리 시간을 합쳐 추정했다. [당시 평가 코드](snapshots/02-gemini-voice-2026-11-16/evaluate_stt.py)

Supertonic으로 만든 짧은 발화 1개, 같은 발화 사이에 쉼을 넣고 이어 붙인 긴 발화 1개, 무음 1개를 사용했다. [테스트 파일 목록](snapshots/02-gemini-voice-2026-11-16/evaluation-fixtures/samples.csv)

| 방식 | 짧은 발화 턴 수 | 긴 발화 턴 수 | 조기 종료 | CER |
|---|---:|---:|---:|---:|
| 5초 고정 녹음 | 1 | 1 | 1건 | 24.1% |
| Silero 기본 이벤트 | 2 | 4 | 2건 | 5.6% |
| 무무 800ms 종료 기준 | 1 | 1 | 0건 | 5.6% |

고정 녹음에서는 긴 발화 뒷부분이 잘렸다. Silero 기본 설정은 말의 내용은 대부분 살렸지만 중간 쉼에서 여러 턴으로 나눴다. 800ms로 기다렸을 때는 이 샘플을 한 턴으로 받으면서 같은 전사 정확도를 유지했다. 무음에서는 두 VAD 방식 모두 Whisper를 호출하지 않았다.

테스트 WAV를 마이크 대신 넣어 실제 Silero·Whisper·Gemini로 두 턴의 응답을 받았다. 두 번째 요청에 첫 턴의 이력이 들어갔고, 종료할 때 스트림이 닫혔다. 기본 마이크의 16kHz 모노 입력도 확인했다.

표는 합성 음성 3개로 확인한 결과다. 여러 화자나 생활 소음이 있는 실제 마이크 환경의 성능까지 보여주는 수치는 아니다.

음성 패키지를 설치한 뒤 루트에서 아래 명령으로 다시 비교할 수 있다. 현재 코드는 이후의 디코딩 변경도 포함하므로 표와 결과가 달라질 수 있다.

```powershell
.\.venv\Scripts\python.exe evaluate_stt.py dev-notes/snapshots/02-gemini-voice-2026-11-16/evaluation-fixtures/samples.csv --silence-ms 800
```

## 5. TTS 탐색과 보류

기존 Supertone을 대신할 한국어 목소리를 찾아봤다. Supertonic 3의 기본 음색 10종을 같은 대사로 비교했고, Qwen3-TTS의 음색 설계와 Chatterbox의 표현 강도·페이스도 살펴봤다.

무무에 쓸 목소리는 정하지 못했다. TTS는 보류하고, 음성 입력과 텍스트 답변까지 만드는 데 집중했다.

## 6. Whisper 전사 정확도 점검

말소리 자체는 잘 잡히는데, 자연스럽게 말하면 다른 단어로 받아쓰는 문제가 있었다. 발화 분리의 영향을 줄이려고 합성 WAV와 800ms 종료 기준을 고정한 뒤 디코딩 설정을 비교했다.

- 기존 `base`는 두 발화를 모두 받아썼지만 “그다음엔”을 “그 다음에”로 인식해 CER이 5.6%였다.
- `small`은 짧은 발화의 해당 표현을 정확히 인식했지만, 같은 문장이 반복되는 긴 WAV에서는 두 번째 문장을 빠뜨렸다. 기존 설정과 `beam_size=5`, `temperature=0` 설정 모두에서 누락됐다.
- 이때는 기본 모델을 `base`로 두고 `beam_size=5`, `temperature=0`을 적용했다. 같은 발화 2개를 실제 `transcribe()`에 넣었을 때 CER은 0.0%였고, 무음에서는 Whisper를 호출하지 않았다.
- 발화별 Whisper 처리 시간은 기존 약 1.5~2.0초, 빔 탐색 적용 후 약 2.8~3.8초였다. 기존 실행 때 다른 모델도 내려받고 있었으므로 시간은 참고만 했다.

이 결과는 같은 합성 문장을 반복한 작은 실험에서 나왔다. 다양한 실제 발화에서 정확도가 올라갔다고 판단하려면 더 비교해야 한다. CLI와 평가 코드에는 `--whisper-model base|small` 선택을 추가했다.

## 7. 레거시 디자인 기반 Flask 화면

끝말잇기에서 “차표”를 다르게 인식하는 문제가 있었다. 이때 무무가 되묻도록 해봤지만 대화가 답답해져 해당 규칙을 지웠다. 구어체 음성 인식 문제는 남겨두고 먼저 화면을 만들었다.

해커톤의 로고와 고양이, 슬로건, 이야기 버튼 이미지를 가져왔다. 크림색 홈 화면과 연두색 대화창 헤더, 사용자 쪽 연두색 말풍선을 살려 Flask로 구성했다. 이후 홈은 이야기와 일기장 버튼으로 바꾸고 슬로건을 없앴다.

텍스트와 음성으로 들어온 말은 같은 대화 함수에 넘겼다. 대화 이력은 브라우저 세션별로 관리하고, 마이크를 켜면 서버 PC의 기본 마이크를 사용하도록 했다. 화면에는 듣는 중인지, 받아쓰는 중인지, 답변 중인지 표시했다.

Edge에서 데스크톱 홈과 모바일 크기의 대화창을 열어 메시지 전송을 확인했다. 실제 Gemini로 두 턴의 문맥 유지도 확인했다. 테스트 WAV를 마이크 대신 넣어 Flask에서도 Silero·Whisper·Gemini가 이어지는 것을 확인했다. 실제 마이크로 화면을 쓰는 과정은 별도로 확인해야 했다.

답변이 너무 길어 대화를 주고받기 어려웠다. 가벼운 반응은 한 문장, 설명이 필요하면 보통 두 문장, 길어도 네 문장 안으로 답하도록 프롬프트를 고쳤다.

## 9. 현재 한국 시각을 대화에 반영

현재 시간을 물었는데 과거 날짜를 답하거나, 잠깐 사이에 시간이 크게 달라지는 문제가 있었다. 매 턴 서버에서 한국 시각(Asia/Seoul)을 새로 읽어 시스템 메시지에 넣었다. 이 시각은 대화 이력에는 저장하지 않았다.

테스트에서는 시계를 15:45:55에서 15:46:05로 바꿔 같은 질문을 두 번 보냈다. 실제 Gemini가 각각 15시 45분과 15시 46분으로 답해 분이 바뀌는 상황에서도 갱신되는 것을 확인했다.

## 10. 한국어 Whisper small 파인튜닝

끝말잇기처럼 짧게 말할 때 다른 단어로 인식되는 문제를 줄이고 싶었다. AI Hub의 한국어 자유대화 샘플을 받아 원본 `openai/whisper-small`에 추가 학습을 했다. WAV와 JSON 전사를 연결하고, 같은 화자가 학습과 평가 양쪽에 들어가지 않도록 나눴다. [첫 학습 노트북](../notebooks/whisper-finetuning.ipynb)

| 항목 | 설정·결과 |
|---|---|
| 학습 | 화자 3명, 발화 1,079개, 약 2시간 |
| 학습 설정 | 1 epoch, 학습률 1e-5, 난수 시드 42 |
| 평가 | 학습에 없는 화자 1명, 발화 120개, 0.26시간 |
| CER | 원본 5.55%, 파인튜닝 4.18%, 차이 1.37%p |

평가에서는 두 모델에 같은 생성 설정을 썼다. CER 계산 전에는 NFC로 정규화하고 띄어쓰기와 문장부호를 뺐다.

로컬 CLI와 평가 코드에서 `fine-tuned`를 선택할 수 있게 연결했다. 무무의 800ms VAD 조건에서 원본 `small`은 긴 합성 WAV의 반복 구간을 빠뜨렸고, 학습한 모델은 그 구간을 받아썼다. 다만 두 모델의 추론 구현은 달랐다. 이 PC의 CPU에서 파인튜닝 모델은 발화당 약 8~11초가 걸렸고, 이 단계에서는 실제 마이크 발화를 평가하지 않았다.

노트북은 출력과 실행 기록을 지운 상태로 저장했다. 데이터는 AI Hub에서 직접 받고, 모델 ZIP은 학습 후 생성하도록 했다.

### 마이크로 써본 뒤 발견한 문제

마이크로 비교해보니 기존 `base`보다 의문문의 물음표가 더 자주 빠졌고, 받아쓰기 자체도 좋아졌다는 느낌이 들지 않았다.

학습 ZIP을 확인해보니 학습 전사 1,079개와 평가 전사 120개 모두에 ASCII·전각 물음표가 하나도 없었다. CER에서도 문장부호를 빼고 있었으므로 이 문제는 점수에 나타나지 않았다. `evaluate_stt.py --question-metrics`에 물음표 누락과 오삽입 집계를 추가하고, 다음 학습은 문장부호가 있는 데이터로 진행하기로 했다.

### KsponSpeech 교차 평가

공식 `eval_clean.trn`의 3,000개 중 물음표로 끝나는 전사는 594개였다. 별도 전사 기호가 없는 한 문장짜리 1.5~5초 음성에서 의문문과 평서문을 10개씩 골랐다. 각 유형에서 3초 미만과 3초 이상을 5개씩 배정했다. 파일명으로 정렬한 후보에서 시드 42로 뽑고, VAD 없이 같은 PCM 구간을 모델에 넣었다.

| 모델 | CER (오류 글자 수 / 정답 글자 수) | 물음표 누락 | 물음표 오삽입 | 로컬 CPU 전사 중앙값 |
|---|---:|---:|---:|---:|
| 기존 base | 11.98% (40/334) | 5/10 | 0/10 | 1.40초 |
| 원본 small | 6.59% (22/334) | 4/10 | 0/10 | 4.03초 |
| 첫 파인튜닝 small | 7.19% (24/334) | 10/10 | 0/10 | 4.78초 |

이 표본에서는 원본 `small`의 CER이 가장 낮았다. 첫 파인튜닝 모델은 `base`보다 CER은 낮았지만 의문문 10개 모두에서 물음표가 빠졌다.

`base`와 원본 `small`은 openai-whisper, 첫 파인튜닝 모델은 Transformers로 실행했다. 짧은 발화 20개를 비교한 결과라 실제 무무 마이크 성능으로 일반화하기는 어렵다.

### KsponSpeech 파인튜닝

이번에는 문장부호가 있는 KsponSpeech로 원본 `small`을 처음부터 다시 학습했다. 학습 발화는 1,812개, 약 2시간이며 1 epoch를 돌렸다. 별도 `eval_clean` 120개를 의문문과 평서문 각 60개로 구성해 같은 추론 설정으로 비교했다. [KsponSpeech 학습 노트북](../notebooks/whisper-ksponspeech.ipynb)

| 지표 | 원본 small | KsponSpeech 파인튜닝 |
|---|---:|---:|
| CER | 10.63% | 9.33% |
| 물음표 누락 | 17/60 | 13/60 |
| 물음표 오삽입 | 6/60 | 7/60 |

웹에서 두 모델을 골라 쓸 수 있게 연결했다. 직접 마이크로 비교했을 때는 원본 `small`이 더 낫다고 판단했다. 그래서 웹의 모델 선택을 없애고 원본 `small`을 쓰기로 했다. 이 마이크 비교에서는 수치를 따로 수집하지 않았다.

### 남겨둔 모델과 가설

| 모델 | 비교 옵션 | 추가 학습 데이터 | 학습 전사의 문장 끝 부호 |
|---|---|---|---|
| 원본 Whisper small | small | 해당 없음 | 해당 없음 |
| 첫 파인튜닝 small | fine-tuned | AI Hub 109번 자유대화, 1,079개·약 2시간 | 마침표·물음표·느낌표로 끝나는 전사 0개 |
| KsponSpeech 파인튜닝 small | ksponspeech | AI Hub 123번 KsponSpeech, 1,812개·약 2시간 | 원래 부호 유지, 물음표로 끝나는 전사 404개 |

성능이 기대만큼 나오지 않은 이유로 두 가지를 생각했다.

1. 원본은 대규모 다국어 음성으로 이미 학습돼 있다. 적은 데이터로 추가 학습하면서 특정 말투나 전사 방식에 치우쳤을 수 있다. [Whisper 논문](https://arxiv.org/abs/2212.04356)
2. 연산 시간 때문에 두 실험 모두 약 2시간의 데이터만 사용했다. 이 정도로는 실제 대화에서 나오는 화자와 발음의 차이를 충분히 담기 어려웠을 수 있다.

아직 검증한 결론은 아니다. 같은 마이크 녹음과 같은 추론 설정으로 비교해야 하고, 데이터 양의 영향을 보려면 학습 표본을 늘려 다시 실험해야 한다. 두 실험은 데이터셋도 다르므로 문장부호만의 효과를 따로 확인한 결과는 없다.

## 11. 레거시 대화 이력과 리버스의 로컬 RAG

해커톤 웹은 현재 대화 이력을 프롬프트에 계속 붙였다. 대화를 끝내면 원문은 `log_DB`, 일기는 `diary_DB`에 파일로 저장했다. 저장한 파일을 다음 대화에서 검색해 쓰는 코드는 없었다. 별도로 만든 CLI에서는 최근 5개 대화 쌍만 모델에 보냈다.

당시 웹의 `IBM-hackathon-program/test/pages/chat.py`에 있는 `build_prompt()`와 종료 처리, CLI의 `test/mumu_cli.py`에 있는 `MAX_HISTORY`와 모델 호출부를 확인했다.

| 항목 | 해커톤 웹 | 현재 Flask 버전 |
|---|---|---|
| 대화 중 | 현재 이력을 프롬프트에 이어 붙임 | 답변 생성에 성공한 턴을 이력으로 전달 |
| 대화 종료 | 원문과 일기를 텍스트 파일로 저장 | 원문과 검색용 벡터, 일기를 SQLite에 저장 |
| 다음 대화 | 현재 세션 이력으로 응답 | 같은 브라우저의 과거 기록에서 관련 구간을 최대 3개 찾아 참고 |
| 일기장 | 저장한 일기를 읽음 | 날짜별 일기와 실제 대화를 말풍선으로 다시 봄 |

### 지금은 어떻게 검색하는가

1. 대화가 끝나면 화자를 구분한 원문을 저장한다. 검색할 구간은 최대 360자로 나눈다. 길이가 허용되면 앞 발화를 다음 구간에 겹쳐 넣어 문맥이 끊기는 것을 줄인다. 임베딩은 LangChain과 `multilingual-e5-small`로 PC에서 만든다. [저장·구간 분리 코드](../memory.py)
2. 사용자가 방금 한 말로 검색한다. 같은 브라우저의 기록에서 코사인 유사도 0.84 이상, 최고 점수와의 차이 0.035 이내인 구간을 최대 3개 고른다. 맞는 기록이 없거나 검색에 실패하면 현재 대화만으로 답한다. [검색 코드](../memory.py) · [웹 대화 처리](../app.py)
3. 찾은 구간을 이번 답변 요청에 참고 자료로 넣는다. 과거 기록의 화자를 구분하고, 지금 사용자가 한 말을 우선하도록 지시한다. [모델 호출 코드](../main.py)

원문과 벡터를 오프라인에서 저장한 뒤, 다음 대화에서 강아지 이름과 무무 초기화에 관한 기록을 찾는 것을 확인했다. 관련 없는 테스트 질문에는 기록을 붙이지 않았고, 다른 브라우저 세션의 기록은 조회되지 않았다.

## 12. 대화 초반의 상황 파악과 사실 근거

시각을 전달하고 있어도 질문을 만들 때는 잘 반영하지 못했다. 아직 오후인데 하루가 끝난 것처럼 묻거나, 실제 날씨를 모르면서 날씨가 좋다고 말을 거는 경우가 있었다.

대화 초반에 상황을 모르면 가벼운 질문 하나로 알아가도록 프롬프트를 고쳤다. 사용자가 먼저 주제를 꺼냈다면 그 이야기를 따라가게 했다. 정해진 횟수만큼 질문하게 만들지는 않았다.

사용자가 알려준 사실과 무무의 추측, 과거 기록을 구분하도록 했다. 예전에 했던 일이나 기분을 오늘의 상황으로 단정하지 않게 하고, 현재 시각을 질문의 시제에도 반영하도록 했다. 날씨와 위치를 조회하는 서비스는 붙이지 않았다.

구문 검사는 통과했다. 실제 대화에서 이런 오류가 얼마나 줄었는지는 측정하지 않았다.

## 13. 답변에 작성 메모가 섞인 사례 대응

“무무를 인간지능까지 개발하고 싶다”는 말에 사용자 의도 분석과 캐릭터 설명이 답변 앞에 함께 나왔다.

LangChain은 별도로 구분된 추론 블록을 텍스트에서 이미 제외하고 있었다. 그래서 이번에는 일반 답변 텍스트에 작성 메모가 섞였을 가능성을 고려했다. Gemini에 `include_thoughts=False`를 명시하고, 사용자에게 할 최종 대사만 출력하도록 프롬프트를 고쳤다.

모의 스트리밍에서 추론 블록이 표시되지 않는 것을 확인했다. 같은 상황을 재구성해 실제 Gemini에 한 번 요청했을 때도 최종 대사만 나왔다. 간헐적으로 다시 생기는지는 더 써보며 확인해야 한다.

## 14. 마감 전 코드 정리와 상태 처리 점검

11월 19일에는 기능을 더 늘리기보다 반복 작업과 상태가 꼬이는 부분을 정리했다.

| 대상 | 바꾼 점 |
|---|---|
| 대화 모델 | 처음 필요할 때 클라이언트를 만들고 재사용. 대화 이력은 세션마다 따로 관리하고, 저장이 끝나면 모델 호출에 쓰던 이력의 참조를 해제 |
| 일기 조회 | 저장된 일기를 읽을 때 다른 일기 생성이 끝날 때까지 기다리지 않도록 수정. 새로 만들 때는 중복 요청인지 다시 확인 |
| 대화 저장 | 빈 대화는 임베딩하지 않고, 재시도 때 이미 저장한 기록을 재사용. 동시에 저장해도 원문과 검색 구간이 서로 섞이지 않도록 수정 |
| 검색 결과 선택 | 조건을 통과한 후보 전체를 정렬하던 코드를 상위 3개만 고르는 방식으로 변경. 유사도 기준과 정렬 순서는 유지 |
| VAD | Torch 추론 모드에서 실행 |
| 타이핑 표시 | 다음 단어가 도착하기 전에는 타이머를 쉬게 함. 대화창에 다시 들어왔을 때 지난 답변을 처음부터 타이핑하던 동작도 수정 |
| 홈 이동 | 답변 도중 홈으로 돌아가도 처리 완료 상태까지 확인하도록 수정 |

생성 중인 답변은 화면에서 약 120ms 간격으로 받아오고, 띄어쓰기 단위로 약 70ms마다 표시한다. 답변이 모두 나타나면 입력창에 포커스를 돌려준다. Enter는 전송, Shift+Enter는 줄바꿈으로 처리했다.

임시 데이터베이스와 모의 모델로 동시 저장, 빈 대화와 반복 저장, 잘못된 벡터, 검색 결과와 사용자 분리, 모델 재사용과 이력 분리, 일기 조회 대기, 스트리밍 실패의 7개 검사를 통과했다. 화면 검사에서는 단어 표시와 타이머, 포커스, 홈 이동, 팝업 종료, 키 입력을 확인했다. 실제 Silero VAD에 무음을 넣는 검사와 Python·JavaScript 구문 검사도 통과했다.

응답 속도와 메모리 사용량이 얼마나 달라졌는지는 측정하지 않았다. 이때는 Git 업로드를 보류했다.
