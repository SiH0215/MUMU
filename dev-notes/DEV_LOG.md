## 1. 텍스트 멀티턴 복원

- 2026-11-13에 레거시 프롬프트를 바이트 그대로 가져와 텍스트부터 연결했다. 시스템 프롬프트를 첫 메시지에 두고, 성공한 사용자 발화와 답변을 순서대로 다음 요청에 전달했다. 응답 실패나 빈 답변이 난 턴은 이력에 남기지 않았다.
- watsonx 초안이 있었으나, 작업 방향에 맞춰 모델 연결을 LangChain의 `init_chat_model()`과 Gemini로 전환했다. 처음에는 터미널에 남아 있던 이전 키가 `.env`의 키보다 먼저 쓰여 결제 한도 오류가 재현됐다. 프로젝트 키를 명시적으로 모델에 전달하도록 바꿨고, 예전 환경 변수가 남아 있던 상태에서 실제 두 턴 응답을 확인했다.
- 실제 호출 시 두 번째 요청의 메시지 역할이 `system → human → ai → human` 순서임을 확인했다. 이전 정보를 다시 묻는 초기 테스트에서는 답변이 빗나간 경우도 있어, 이력 전달과 모델의 답변 품질을 구분해 기록했다.

## 2. 무무 프롬프트 다듬기

- 해커톤 프롬프트를 기준으로 맥락 회상과 정정 규칙을 구체화한 버전을 시험했다. 이후 캐릭터 설정부터 다시 다듬기로 하면서, 가벼운 한국어 반말과 다정한 태도를 중심으로 줄였다.
- 최종 상태에서는 순수함이 말투와 태도에 드러나도록 하고, 질문에는 맥락과 의도를 읽어 필요한 만큼 정확히 답하도록 했다. 작별 의도가 명확하면 질문을 붙이지 않고 인사하도록 했다. CLI 종료 명령은 `/exit`다.
- 현재 문구는 [스냅샷의 시스템 프롬프트](snapshots/02-gemini-voice-2026-11-16/SYSTEMPROMPT.txt)에서 볼 수 있다. 중간 프롬프트 단계는 이 기록에 요약했다.

## 3. 고정 녹음에서 발화 단위 입력으로

**기존 방식.** 해커톤 채팅 페이지는 발화 길이와 관계없이 16kHz로 5초를 녹음했다. 폴더의 정리본은 Whisper 모델 재사용을 지원했다. 5초를 넘는 입력의 말끝 누락과 짧은 발화 이후의 남는 대기 시간을 비교 대상으로 잡았다.

**현재 방식.** `main.py --voice`에서 마이크를 켜고, 완료된 전사문을 기존 채팅 함수에 전달한다. 캡처 스레드와 전사·응답 처리를 분리해 Gemini 응답을 기다리는 중에도 마이크를 읽는다. 마이크 입력이 넘치면 발화 버퍼를 초기화하고, 처리 대기열이 꽉 차면 해당 발화를 건너뛰었다고 표시한다.

- [voice.py](snapshots/02-gemini-voice-2026-11-16/voice.py)는 16kHz 모노 PCM을 512샘플씩 읽는다. Silero VAD에서 발화 확률을 구하고, 완료된 구간을 로컬 Whisper `base`로 한국어 전사한다. Whisper 모델은 세션 시작에 한 번 로드한다. PCM을 파형 배열로 바꿔 전달해 임시 녹음 파일 없이 처리한다.
- [turns.py](snapshots/02-gemini-voice-2026-11-16/turns.py)는 32ms 프레임을 한 턴으로 묶는다. 발화 시작 임계값은 0.50, 유지 임계값은 0.35다. 시작 전 최대 224ms를 붙이고, 기본 800ms 동안 말소리가 없으면 턴을 확정한다. 그 전에 말소리가 다시 감지되면 같은 턴으로 이어진다. 끝의 무음은 약 96ms만 남기고, 아주 짧은 감지 신호는 버린다.
- Windows의 한글 경로에서 Silero TorchScript 파일을 직접 열 때 오류가 났다. 모델 파일을 파이썬에서 바이트로 읽어 메모리 버퍼로 TorchScript에 넘기는 방식으로 해결했다.

## 4. STT 비교와 검증 결과

[evaluate_stt.py](snapshots/02-gemini-voice-2026-11-16/evaluate_stt.py)는 동일한 WAV를 **5초 고정 녹음**, **Silero 기본 이벤트**, **무무의 800ms 종료 규칙**으로 나눠 같은 Whisper 모델에 넣는다. 글자 오류율(CER), 조기 종료, 미전사, 무발화 오인식을 집계한다. 대기 시간 지표는 WAV의 감지 시각에 실제 Whisper 처리 시간을 합친 추정치다.

[합성 테스트 목록](snapshots/02-gemini-voice-2026-11-16/evaluation-fixtures/samples.csv)은 Supertonic으로 만든 짧은 발화 1개, 같은 발화를 중간 쉼과 함께 이어 붙인 긴 발화 1개, 무음 1개로 구성했다.

| 방식 | 짧은 발화 턴 수 | 긴 발화 턴 수 | 조기 종료 | CER |
|---|---:|---:|---:|---:|
| 5초 고정 녹음 | 1 | 1 | 1건 | 24.1% |
| Silero 기본 이벤트 | 2 | 4 | 2건 | 5.6% |
| 무무 800ms 종료 규칙 | 1 | 1 | 0건 | 5.6% |

고정 녹음은 긴 발화 뒷부분을 잘랐다. Silero 기본 이벤트는 전사된 내용을 대부분 살렸지만 중간 쉼에서 발화를 여러 턴으로 나눴다. 800ms 설정은 이 샘플에서 같은 전사 정확도를 유지하며 한 턴으로 묶었다. 무음에서 두 VAD 방식 모두 Whisper를 호출하지 않았다.

- 한국어 WAV를 마이크 스트림 대신 재생해 실제 Silero·Whisper·Gemini가 연결된 상태로 두 턴 응답을 확인했다. 두 번째 요청에 첫 턴의 이력이 포함됐고, 종료 시 스트림이 닫혔다.
- 기본 마이크가 16kHz 모노 입력을 지원하는 것은 확인했다. 실제 마이크 발화, 여러 화자와 소음 환경에서의 실사용 검증은 남아 있다.
- 표의 수치는 작은 합성 샘플로 동작을 확인한 결과다. GitHub에서 실사용 개선 수치를 쓰려면 짧은 응답, 긴 발화, 중간 쉼, 생활 소음을 포함한 실제 녹음을 모으고, 종료 기준을 조정한 녹음과 최종 검증용 녹음을 나눠 비교한다.

보존한 WAV로 비교를 다시 실행할 수 있다. 리버스 프로젝트 루트에서 음성 패키지를 설치한 뒤 실행한다. 현재 코드에는 아래의 디코딩 변경이 포함되어 있어 이 표와 다른 결과가 나올 수 있다.

```powershell
.\.venv\Scripts\python.exe evaluate_stt.py dev-notes/snapshots/02-gemini-voice-2026-11-16/evaluation-fixtures/samples.csv --silence-ms 800
```

## 5. TTS 탐색과 보류

기존 Supertone API를 대체할 한국어 보이스를 조사했다. Supertonic 3의 기본 음색 10종을 같은 한국어 대사로 비교했고, Qwen3-TTS의 음색 설계와 Chatterbox의 표현 강도·페이스를 검토했다. 무무에 쓸 최종 음색은 확정하지 않았다. 현재 스냅샷은 STT와 텍스트 응답까지 구현된 상태다.


## 6. Whisper 전사 정확도 점검

실사용에서 전사 정확도가 낮게 느껴진다는 피드백을 받았다. 발화 분리의 영향을 줄이기 위해 보존한 합성 WAV와 800ms 종료 기준을 고정하고 디코딩을 비교했다.

- 기존 Whisper `base`는 두 발화를 모두 전사했지만 “그다음엔”을 “그 다음에”로 받아써 CER이 5.6%였다.
- Whisper `small`은 짧은 발화의 해당 표현을 정확히 받았지만, 같은 문장이 이어지는 긴 WAV에서 두 번째 문장을 빠뜨렸다. 기존 디코딩과 `beam_size=5`, `temperature=0` 설정 모두에서 이 누락을 확인했다.
- 기본 모델은 `base`로 유지하고, 디코딩을 `beam_size=5`, `temperature=0`으로 바꿨다. 실제 코드의 `transcribe()`로 확인한 결과, 같은 발화 2개에서 CER은 0.0%였고 무음에서 Whisper는 호출되지 않았다.
- 실험에서 발화별 Whisper 처리 시간은 기존 약 1.5~2.0초, 빔 탐색 적용 후 약 2.8~3.8초였다. 기존 실행 중에는 다른 모델을 다운로드하고 있어 시간은 참고용이다. 같은 합성 문장을 반복한 소규모 테스트라 다양한 실제 발화에 대한 정확도는 추가 검증이 필요하다.

음성 채팅과 평가 스크립트에 `--whisper-model base|small` 선택을 추가했다.

## 7. 레거시 디자인 기반 Flask 화면

- 끝말잇기 STT 오류에서 무무가 되묻도록 넣었던 규칙을 제거하고, 구어체 전사 품질 개선은 이후 과제로 남겼다.
- 해커톤의 로고, 고양이, 슬로건과 이야기 버튼 이미지를 옮겼다. 홈은 원본의 크림색, 이야기 화면은 연두색 헤더와 사용자 쪽 연두색 말풍선을 유지하도록 구성했다.
- Flask가 브라우저 세션별 대화 상태를 유지한다. 텍스트와 Whisper 전사문은 같은 LangChain 멀티턴 처리에 전달된다. 마이크를 켜면 서버 PC의 기본 마이크를 사용하며 발화 수집, 전사, 응답 상태를 화면에 표시한다.
- Edge에서 데스크톱 홈과 모바일 채팅 화면의 렌더링 및 전송을 확인했다. 실제 Gemini로 두 텍스트 턴의 문맥 유지를 확인했고, 테스트 WAV를 마이크 대신 공급해 실제 Silero·Whisper·Gemini의 Flask 음성 경로도 검증했다. 실제 마이크 발화로 웹의 사용성은 추가 확인이 필요하다.

가벼운 대화에는 한 문장, 더 설명할 때는 보통 두 문장, 자세한 질문에도 최대 네 문장으로 답하도록 시스템 프롬프트에 길이 기준을 추가했다.

## 9. 현재 한국 시각을 대화에 반영

무무가 과거 날짜나 서로 다른 시각을 답하는 사례가 있었다. 매 턴 새로 읽은 서버 시각을 한국 시간(Asia/Seoul)으로 변환해 시스템 메시지에 전달한다. 시간이 들어간 시스템 메시지는 대화 이력에 저장하지 않는다.

Flask에서 실제 Gemini에 같은 시각 질문을 두 번 보냈다. 테스트 시계를 15:45:55에서 15:46:05로 바꿨을 때 각각 15시 45분과 15시 46분으로 답해 분 경계에서 갱신되는 것을 확인했다.

## 10. 한국어 Whisper small 파인튜닝

끝말잇기처럼 짧은 구어체가 다른 단어로 전사되는 사례를 계기로 한국어 자유대화 데이터에서 전사 성능을 비교했다. [학습 노트북](../notebooks/whisper-finetuning.ipynb)은 AI-Hub 샘플의 WAV와 JSON 전사를 매칭하고, 화자가 겹치지 않도록 학습과 평가를 나눈다.

- **학습**은 화자 3명의 발화 1,079개(2시간)로 `openai/whisper-small`을 1 epoch 파인튜닝했다. 학습률은 `1e-5`, 난수 시드는 `42`였다.
- **평가**는 별도 화자 1명의 발화 120개(0.26시간)에서 같은 생성 설정으로 수행했다. CER 계산 전 텍스트를 NFC로 정규화하고 띄어쓰기와 문장부호를 제외했다. 원본 CER **5.55%**, 파인튜닝 CER **4.18%**, 차이는 **1.37%p**였다.
- **로컬 연결** 후 앱과 평가 스크립트에서 `fine-tuned`를 선택할 수 있게 했다. 무무의 800ms VAD 조건에서 기존 `small`은 긴 합성 WAV의 반복 구간을 빠뜨렸고, 파인튜닝 모델은 해당 구간을 전사했다. 두 모델은 서로 다른 추론 구현을 사용했으며, 이 PC의 CPU에서 파인튜닝 모델의 전사 시간은 발화당 약 8~11초였다. 실제 마이크 발화는 아직 평가하지 않았다.

학습 노트북은 결과 출력과 실행 기록을 제거한 형태로 저장한다. 학습 데이터는 AI-Hub에서 직접 받고, 모델 ZIP은 노트북에서 생성한다.

### 마이크 시연 후 점검

실제 마이크 시연에서 사용자는 기존 `base`보다 파인튜닝 모델이 의문문 끝의 물음표를 빠뜨리고 전사 품질도 떨어진다고 보고했다. ZIP을 확인한 결과 학습 전사 1,079개와 평가 전사 120개 전체에서 ASCII·전각 물음표가 각각 0개였다. 기존 CER은 문장부호를 제외하므로 이 차이를 반영할 수 없다. 다음 평가에서 사용할 수 있도록 `evaluate_stt.py --question-metrics`에 문장 끝 물음표 누락과 오삽입 집계를 추가했다. 다음 학습에서는 문장부호가 포함된 전사를 사용하고, 같은 무무 마이크 녹음에서 기존 `base`와 비교한다.

### KsponSpeech 교차 평가

공식 `eval_clean.trn` 3,000개 중 물음표로 끝난 전사는 594개였다. 전사가 문장 하나이고 별도 전사 기호가 없는 1.5~5초 음성 중 의문문 10개와 평서문 10개를 골랐다. 문장 유형마다 3초 미만과 3초 이상의 발화를 5개씩 배정했고, 파일명순으로 정렬한 후보에서 시드 42로 추출했다. VAD 없이 동일한 PCM 구간을 각 모델에 입력했다.

| 모델 | CER (오류 글자 수 / 정답 글자 수) | 물음표 누락 | 물음표 오삽입 | 로컬 CPU 전사 중앙값 |
|---|---:|---:|---:|---:|
| 기존 `base` | 11.98% (40/334) | 5/10 | 0/10 | 1.40초 |
| 원본 `small` | 6.59% (22/334) | 4/10 | 0/10 | 4.03초 |
| 기존 파인튜닝 `small` | 7.19% (24/334) | 10/10 | 0/10 | 4.78초 |

이 표본에서 원본 `small`은 세 모델 중 CER이 가장 낮았다. 기존 파인튜닝 모델은 `base`보다 CER이 낮았지만 의문문 10개의 물음표를 모두 누락했다. `base`와 원본 `small`은 openai-whisper, 기존 파인튜닝 모델은 Transformers를 사용했다. 표본은 KsponSpeech의 짧은 발화 20개로, 무무의 실제 마이크 전사 정확도나 응답 시간을 추정하는 데에는 별도의 평가가 필요하다.

### KsponSpeech 파인튜닝

[후속 학습 노트북](../notebooks/whisper-ksponspeech.ipynb)에서 원본 `openai/whisper-small`을 문장부호가 들어 있는 KsponSpeech 학습 발화 1,812개(약 2시간)로 1 epoch 학습했다. 별도 `eval_clean` 120개(의문문·평서문 각 60개)에서 같은 추론 설정으로 비교한 결과, CER은 10.63%에서 9.33%로, 물음표 누락은 17건에서 13건으로 줄었고, 오삽입은 6건에서 7건으로 늘었다. 무무 웹 대화 화면에서 원본과 KsponSpeech 모델을 선택할 수 있게 연결했다.

사용자가 실제 마이크로 비교한 결과 원본 `small`의 전사가 더 좋다고 판단했다. 웹에서 모델 선택을 제거하고 원본 `small`을 채택했다. 실제 마이크 비교는 정량 지표를 따로 수집하지 않았다.

### 보존한 세 모델과 후속 가설

| 모델 | 비교 옵션 | 추가 학습 데이터 | 학습 전사의 문장 끝 부호 |
|---|---|---|---|
| 원본 Whisper `small` | `small` | 해당 없음 | 해당 없음 |
| 첫 파인튜닝 `small` | `fine-tuned` | AI Hub 109번 자유대화, 1,079개·약 2시간 | 마침표·물음표·느낌표로 끝나는 전사 0개 |
| KsponSpeech 파인튜닝 `small` | `ksponspeech` | AI Hub 123번 KsponSpeech, 1,812개·약 2시간 | 원본 부호 보존, 물음표로 끝나는 전사 404개 |

1. **원본 모델이 다양한 발화에 더 잘 일반화했을 가능성.** Whisper는 대규모 다국어 음성으로 사전학습되었다. 제한된 말투와 전사 규칙을 가진 데이터로 추가 학습하면 해당 데이터의 평가 점수는 좋아져도, 무무의 짧은 대화나 마이크 환경에서는 원본보다 오류가 늘 수 있다. 같은 무무 녹음에서 세 모델을 비교하고, 짧은 발화·연음과 축약·말 중간의 쉼처럼 유형별로 오류를 확인한다. [Whisper 사전학습 논문](https://arxiv.org/abs/2212.04356)
2. **약 2시간의 학습 표본이 무무에서 만나는 발화의 변이를 충분히 담지 못했을 가능성.** 제한된 연산 시간으로 두 실험을 각각 2시간가량의 데이터로 진행했다. 데이터 양의 영향을 확인하려면 KsponSpeech 안에서 기존 2시간 표본을 포함하는 더 큰 학습 표본을 만들고, 모델 초기값·전사 처리·학습률·업데이트 횟수·평가 세트를 고정해 비교한다. 화자와 발화 유형의 분포도 함께 기록한다.

두 가설은 아직 검증하지 않았다. 세 모델을 같은 무무 녹음과 동일한 추론 구현·디코딩 설정에서 평가할 때 CER과 물음표 누락·오삽입을 따로 집계한다. 두 파인튜닝 실험은 데이터셋 자체가 다르므로, 문장부호 보존만의 효과를 보려면 같은 음성과 정답으로 문장부호 처리만 바꾼 실험이 필요하다.

## 11. 레거시 대화 이력과 리버스의 로컬 RAG

해커톤 웹은 진행 중인 대화 이력을 프롬프트에 이어 붙였다. 대화를 끝내면 원문을 `log_DB`에, 일기 요약을 `diary_DB`에 파일로 저장했다. 이 저장 파일을 새 대화의 답변에 검색해 넣는 경로는 웹 코드에 없었다. 별도의 레거시 CLI는 현재 대화에서 최근 5개 대화 쌍만 모델에 전달했다. 레거시 확인 위치는 `IBM-hackathon-program/test/pages/chat.py`의 `build_prompt()`와 종료 처리, `test/mumu_cli.py`의 `MAX_HISTORY`와 모델 호출부다.

| 비교 항목 | 레거시 웹 | 리버스 Flask |
|---|---|---|
| 진행 중인 대화 | 현재 대화의 이력을 프롬프트에 이어 붙임 | 현재 대화의 성공한 턴을 이력으로 전달 |
| 끝난 대화의 저장 | 원문과 일기 요약을 텍스트 파일로 보관 | 원문과 구간별 벡터를 로컬 SQLite에 저장 |
| 새 대화에서 활용 | 현재 세션의 대화 이력으로 응답 | 같은 브라우저가 저장한 과거 기록에서 관련 구간을 최대 3개 찾아 참고 |
| 일기장 | 종료 시 생성한 일기 요약을 열람 | 종료 시 무무 시점의 일기를 별도로 저장. 날짜별 일기 본문과 읽기 전용 말풍선으로 대화 전문을 열람 |

### 리버스에서 바뀐 흐름

1. 대화가 끝나면 화자 정보를 유지한 원문을 저장한다. 검색용 원문은 구간당 최대 360자로 나누고, 길이가 허용되면 인접 구간에 앞 발화를 겹쳐 둔다. LangChain과 `multilingual-e5-small`로 로컬에서 임베딩해 SQLite에 보관한다. [저장 및 구간 분리 코드](../memory.py)
2. 일반 발화가 들어오면 직전 입력을 검색어로 사용한다. 같은 브라우저의 저장 기록에서 코사인 유사도가 0.84 이상이고 최고 점수와 0.035 이내인 항목을 최대 3개 고른다. 조건을 만족하는 기록이 없거나 검색에 실패하면 현재 대화 이력으로 답한다. [검색 코드](../memory.py) · [Flask 응답 흐름](../app.py)
3. 검색된 구간은 해당 답변 요청에 참고 자료로 붙인다. 대화 모델은 현재 입력을 우선하고, 과거 발화가 누구의 말인지 구분하도록 지시받는다. [대화 모델 호출](../main.py)

### 확인한 개선

- 오프라인 상태에서 대화 원문과 벡터를 저장하고, 다음 대화에서 강아지 이름과 무무 초기화 이야기에 해당하는 구간을 검색했다.
- 관련 없는 테스트 질문에는 과거 기록을 붙이지 않았고, 다른 브라우저 세션에서는 해당 기록을 조회할 수 없음을 확인했다.

## 12. 대화 초반의 상황 파악과 사실 근거

현재 한국 시각을 전달하고 있었지만, 질문의 시제나 화제 선택에도 활용하도록 지시하지는 않았다. 사용자가 알려주지 않은 날씨나 활동을 전제로 말을 거는 문제에 대응해 시스템 프롬프트에 상황 판단 규칙을 추가했다.

- 새 대화에서 상황이 부족하면 가벼운 질문 하나로 알아가며, 사용자가 주제를 제시하면 그 내용을 따라간다. 고정된 정보수집 턴 수는 두지 않았다.
- 사용자 발화, 무무의 추측, 과거 기록을 구분하고, 과거의 활동이나 기분을 오늘의 사실로 옮기지 않도록 했다.
- 현재 시각을 질문과 시제 선택에도 활용하도록 요청별 지침을 보강했다. 날씨나 위치를 확인하는 외부 서비스는 연결하지 않았다.

파이썬 구문 검사를 통과했다. 실제 대화에서의 맥락 오류 감소는 아직 측정하지 않았다.

## 13. 답변에 작성 메모가 섞인 사례 대응

사용자가 무무를 인간지능까지 개발하고 싶다고 말한 뒤, 사용자 의도 분석과 캐릭터 지침이 최종 대사 앞에 함께 출력된 사례가 있었다. LangChain의 텍스트 추출은 별도로 구분된 추론 블록을 이미 제외하므로, 일반 답변 텍스트로 생성된 작성 메모의 혼입 가능성을 고려했다.

Gemini 모델 생성 시 `include_thoughts=False`를 명시하고, 시스템 프롬프트에 최종 대사만 출력하도록 지시했다. 모의 스트리밍에서 추론 블록이 표시 텍스트에 섞이지 않음을 확인했다. 제시된 상황을 재구성한 실제 Gemini 스트리밍 호출 1회에서도 최종 대사만 반환됐다. 간헐적 재발 여부는 추가 사용 중 확인이 필요하다.

## 14. 마감 전 코드 정리와 상태 처리 점검

2026년 11월 19일, 현재 기능을 유지하면서 반복 생성과 불필요한 처리를 정리했다.

| 대상 | 변경 |
|---|---|
| 대화 모델 | Flask 앱에서 모델 클라이언트를 지연 생성한 뒤 재사용. 세션별 대화 이력은 독립적으로 유지하고, 저장이 끝난 대화의 모델 이력 참조를 해제 |
| 일기 조회 | 이미 저장된 일기는 다른 일기의 생성 잠금을 기다리지 않고 조회. 생성이 필요한 경우 잠금 안에서 저장 여부를 다시 확인 |
| 원문과 검색 구간 저장 | 빈 대화는 임베딩하지 않고, 재시도는 기존 저장을 재사용. 동일 기록에 대한 동시 요청에서는 원문을 처음 저장한 요청만 검색 구간을 함께 저장 |
| RAG 후보 선택 | 유사도 조건을 통과한 후보 전체를 정렬하던 처리를 상위 3개 선택으로 변경. 기존 임계값과 정렬 우선순위 유지 |
| 음성 감지 | VAD 호출에 Torch 추론 모드를 적용 |
| 화면 상태 | 다음 어절이 도착하기 전에는 타이핑 타이머를 쉬게 하고, 대화창 재진입 시 과거 답변은 즉시 표시. 홈으로 돌아간 뒤에도 진행 중인 응답은 마무리 상태까지 조회 |

임시 데이터베이스와 모의 모델로 동시 저장, 빈 대화와 반복 저장, 잘못된 벡터의 저장 방지, 검색 상위 3개와 사용자 분리, 모델 재사용과 대화 이력 분리, 일기 생성 중 다른 일기 조회, 스트리밍 실패 시 이력 보존의 7개 회귀 검사를 통과했다. 화면 로직 검사에서 어절 경계, 대기 중 타이머 정지, 최종 단어 표시, 포커스 복귀, 홈에서의 조회 중단, 로딩 팝업 종료, Enter와 Shift+Enter 처리를 확인했다. 실제 Silero VAD에 무음 프레임을 입력하는 검사와 Python·JavaScript 구문 검사도 통과했다.

응답 속도나 메모리 사용량의 개선 수치는 측정하지 않았다. Git 작업은 보류했다.
